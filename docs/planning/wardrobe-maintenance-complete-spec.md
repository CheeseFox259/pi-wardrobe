# Complete Update / Maintain execution

Status: user requirements settled on 2026-11-16; implementation and verification pending. Local specification; no remote publication authorized.

## Problem Statement

Preset updates can accumulate sound decisions without finishing their promised adaptations. A compound request becomes one unbounded integration item, compact responses hide its actionable context, and recovery asks for generic delivery. Paid chains repeatedly discover these connected defects too late.

## Solution

Keep one shared method and one preset-owned product policy. Component maintenance contracts settle product defaults. The existing workflow ledger also tracks bounded implementation items, linked to source requirements/decisions, candidate paths, expected outcomes, checks, dependencies and concrete missing facts. The current model decomposes compound work through the public tool; the program validates structural coverage and eligibility without claiming to understand all natural-language semantics. Simple maintenance remains a single item.

## User Stories

1. As a preset maintainer, I want component defaults and user-override boundaries so repeated maintenance preserves established choices.
2. As a user, I want all parts of a compound request represented before completion so a final catch-all cannot hide unfinished work.
3. As an executing model, I want to add implementation items while saving decisions so planning requires no separate model or session.
4. As a maintainer, I want saved decisions distinguished from implementation claims and checked behavior.
5. As an executing model, I want relevant facts, paths and original evidence at focus so I can act without inspecting manager internals.
6. As an executing model, I want to record a named missing fact before broadening investigation, without a management call for each read or edit.
7. As a user, I want blockers to preserve finite next steps while independent work continues.
8. As a maintainer, I want exact affected checks before final verification, in the actual staged candidate and isolated environment.
9. As a user, I want stale implementation/check evidence invalidated when the candidate changes.
10. As a user, I want native quota/cancellation recovery to preserve requirements, implementation items and budget evidence.
11. As an operator, I want bounded recovery to name outstanding work, while repeated narrative saves do not renew its budget indefinitely.
12. As a preset author, I want conservative fallback without Perfect Pi-specific rules in the shared manager.
13. As a user, I want final verification, inactive installation and unchanged startup defaults to remain mandatory.
14. As an operator, I want known protocol and acceptance defects covered without a paid model request before the next full-chain run.

## Implementation Decisions

- Extend existing work items, partial submissions and journal persistence. Implementation items have stable IDs, origins, goals, safe relative paths, sparse dependencies, affected checks, an implementation claim and optional named missing facts.
- Claims record the exact candidate identity; changes invalidate claims conservatively. They never substitute for actual checks. Optional upstream deferral and required explicit requests retain distinct semantics.
- Decomposition explicitly covers the originating request or decision and declares a bounded set of child items. The parent is decided only after its decisions and necessary children are ready. Coverage is structural; independent frozen product acceptance checks remain necessary.
- New explicit requests use tracked implementation from the start. Existing saved records retain readable state and require conservative completion, not inferred implementation from prose. Existing ordinary update decisions continue to use program-owned adoption.
- The model can submit planning, implementation, checks and blockers in the same save. Schema errors reject the entire change before journal mutation. Unknown references, unsafe paths and dependency cycles are actionable errors.
- Focus remains a view. Cross-item saves and independent work remain available. Repeated focus on the same item does not grant a fresh correction allowance.
- Focused responses retain implementation goals, missing facts, linked decisions, contract pointers, original evidence excerpts and public manager APIs. Large historical narratives remain available through details and original paths.
- Partial checking uses actual staged dependencies, isolated HOME/Pi and exact checks. Its evidence is separate from final eligibility and reused only for matching candidate/check/dependency/runtime identities.
- Recovery reports unresolved implementation outcomes or missing decisions. Only substantive candidate/decision/implementation/check progress renews delivery; changing summaries or missing-fact prose alone does not.
- Program-owned final verification continues to apply automatic adoption, validate resources/lineage/preservation, run affected checks and seal the current artifact. No partial check permits installation.
- Policy specifies product contracts; shared skills specify execution. A component reference document can carry detailed contracts without replaying them on every receipt.

## Testing Decisions

The primary seam is the existing public workflow tool; observe results, candidate behavior, final receipts and unchanged configuration. Existing native scripted-provider tests supply runtime control-path evidence. Test compound planning through install, transactional rejection, unresolved and stale work, dependencies, partial checks, recovery, compact context and restart. Keep historical failures as negative cases. Run relevant regressions and the repository suite after integration; do not equate deterministic provider evidence with real-model efficiency.

Before payment, replay relevant historical artifacts in isolated copies, validate acceptance helpers, and freeze independent product expectations and source/helper hashes. A new paid chain measures the whole path with the authorized model. Product failures remain sealed; accidental interruption recovery follows the existing runbook with cumulative budgets.

## Out of Scope

Unrelated preset features, remote publication, commits/pushes, native model/authentication changes, a separate planning provider, a second preset-specific workflow, shell semantic classification, and a promise to eliminate unknown failures.
