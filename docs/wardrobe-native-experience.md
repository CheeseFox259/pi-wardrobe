# Wardrobe 原生 Pi 使用体验

> 后续调整：Pi/extension 更新交回原生 `pi update`；Wardrobe 负责 preset 源码与上游 skill 维护。统一预设列表、创建/编辑草稿和通用本地导入已替代下文早期菜单与迁移入口。当前操作见[中文指南](usage.zh-CN.md)，新流程与验收见[预设重设计](planning/wardrobe-preset-redesign.md)。

状态：Q1–Q7 已实现于本机工作区，尚未发布远端。2026-10-19。日常操作见 [中文指南](usage.zh-CN.md)。

## 已确认的行为

1. 日常入口是原生 `pi`，管理入口是 composer 中的 `/wardrobe`。后续 preset 的导入、安装、切换、更新和启动默认值设置在 Pi 中完成。
2. 切换 preset 只影响当前会话，默认新建对话。旧对话保留，可恢复；不偷偷改变下次启动的选择。
3. 独立提供“设为启动默认”。项目默认优先于全局默认；恢复历史对话时优先使用该对话的绑定。
4. 优先升级整套 preset，也支持单独升级 skill/extension 所属资源，并保存为有来源记录的本地派生版本。
5. 首次使用将全局资源和偏好整理为“我的原始配置” preset；项目配置继续按 Pi 的信任和加载规则单独生效。
6. 模型、认证、模型默认值和相关模型配置始终由原生 Pi 管理，不进入 preset，不要求重新登录。
7. extension 变化时可以由 Pi 在同一终端自动交接到新进程，确保旧扩展状态清理。用户无需退出后再输入启动命令。

## 改动前的诊断证据

改动前已有 `/wardrobe` 扩展，但主要是文本子命令；完整资源切换仍输出外部启动计划。`perfect-pi update` 更新本地源码快照，固定 Git/npm 依赖不会因此自动升级，也没有统一的 Pi 本体更新界面。

真实 TUI 的最小隔离测试，不读取个人认证、不调用模型：

| 场景 | 到达 TUI 的耗时 |
| --- | ---: |
| 原生 Pi | 528 ms |
| Wardrobe，存在同名 skill | 1,401 ms |
| Wardrobe，跳过启动探测 | 690 ms |
| Wardrobe，无同名 skill | 976 ms |

同一测试配置中，额外探测约增加 0.7 秒；同名 skill 会增加一次 Pi 探测。测试命令：`node .scratch/wardrobe-native-experience/startup-loop.mjs`。以已确认的额外耗时 500 ms 预算衡量，旧路径失败。

本机两个已安装的完整 Perfect Pi 版本各包含约 14,800 个受锁文件、85 MB 代码。只读完整诊断分别耗时 2,336 ms、2,429 ms。现有启动前检查和会话初始化都会调用全版本诊断，耗时随保留版本增长。以上是分段测量，不冒充用户完整环境的 10 秒启动实测。

进一步只复制两个版本的公共包树、计划和安装元数据到隔离目录，在原生与 Wardrobe 两条路径中同时禁用第三方 extension，避免 MCP 和私密运行数据影响：原生 672 ms，Wardrobe 3,801 ms，额外 3,129 ms。命令：`node .scratch/wardrobe-native-experience/full-tree-startup-loop.mjs`。这是已预热文件系统上的 Wardrobe 开销下限，不能与上一段不同缓存条件的分段数字直接相加，也不能代表完整启用全部扩展时的启动总耗时。

自动交接实验使用真实 Pi 1.1.0 TUI，在 macOS/Node 26.5.0 上验证 composer 命令、旧实例 shutdown、新进程同 PID、新对话、旧对话保留和恢复。无外部启动器；`process.execve` 在正常终端清理后替换进程。命令：`node .scratch/wardrobe-native-experience/handoff-loop.mjs`。尚未验证 Windows、任意第三方扩展和进程替换失败恢复。

Pi 支持 `ctx.reload()`、`ctx.newSession()` 和 `ctx.switchSession()`。资源重载会重建命令与工具，但不能保证任意扩展自行创建的定时器和全局副作用消失。`resources_discover` 只支持补充 skill、prompt、theme；没有公开的会话级完整 extension/profile 切换接口。因此不能把全部切换伪装成可靠的热加载。

## 已实现的使用流程

### 初次接入

用户只需按原生 Pi 的包安装方式接入 Wardrobe 扩展一次。扩展尚不存在时，不能承诺所有 bootstrap 步骤都在它自己的菜单中完成；提供一个原生安装命令，随后重载或正常打开 Pi。

首次 `/wardrobe` 展示迁移摘要：资源数量、资源来源、可纳入的偏好、保持由 Pi 管理的配置，以及无法自动归档的本地依赖。一次确认后生成“我的原始配置”，保存原配置备份及迁移记录，并设为初始全局默认。失败保持原使用方式；不进行半完成的配置接管。

整理过程应复制本地资源或保存明确的本机依赖引用，不删除共享的 `~/.agents/skills`，不修改其他工具使用的个人技能文件。不扫描并打包整个用户目录。凭据及私密扩展配置保留在原生或本机私密存储；导出时明确列出不能随 preset 分享的依赖。

### 日常使用

输入 `/wardrobe` 打开可搜索的原生 TUI 面板：

- Presets：当前使用、安装版本、来源、全局默认/项目默认标记；选择后可使用、查看、设为默认或移除。
- 导入：粘贴 GitHub 仓库地址；有多个 preset 时选择一个，展示资源和变更摘要，确认后安装。
- 更新：区分 Pi 本体、Wardrobe、preset、独立资源；展示当前与目标版本、兼容性、变更摘要和结果。
- 当前会话：显示实际使用的 preset/修订、待启用更新和旧对话恢复入口。

保留可补全的命令入口供熟练用户使用，但不要求记住内部 plan ID、digest 或安装目录。菜单确认绑定同一个不可变计划，不能先确认一份内容再安装另一份。

### 切换和恢复

“使用此 preset”先完成必要的安装和检查，成功后才交接；默认新建对话并保留返回旧对话的入口。启动默认值保持不变。正在执行工具或模型请求时不打断，提示等待空闲或取消。

恢复历史对话同时恢复其 preset 绑定和必要的资源版本，不把旧对话直接放进当前不同的环境；版本缺失时在 Pi 中提供恢复安装。原生 `/resume`、`/tree` 也必须遵守绑定，不能仅让 Wardrobe 自己的菜单正确。

extension 变化采用自动进程交接，先运行原生清理，随后替换当前 Pi 进程，不创建留在后台的外部管理器。skill/prompt/theme 的变化可以复用已验证的原生重载能力；无论内部走哪条路径，默认都新建对话。

### 更新

检查更新不阻塞 TUI，不在普通启动时自动下载或升级。更新页先展示本地状态，再异步获取远端结果；离线可以继续使用已安装版本。

- 整套更新：根据稳定仓库身份和更新通道解析新发布/提交，生成新计划和修订；保留旧版和历史对话绑定。固定安装版本与跟踪更新的上游位置是两项不同信息。
- 独立资源更新：skill/extension 如果属于一个 npm/Git 包，实际升级该包，并说明同时涉及的其他资源；不声称一个文件拥有独立发布版本。保存为本地派生 preset，不覆盖作者版本。
- 本地派生版本追随上游：保留本地变更，显示与新上游冲突的字段或资源，不能静默覆盖。
- Pi 本体：调用当前安装方式对应的原生自更新能力，而不是由 Wardrobe 安装第二套 Pi。先检查 preset 与目标 Pi 版本的兼容性；不支持的安装方式明确展示可执行的下一步，不假装更新成功。
- 启用：安装完成后可“现在使用”或“下次启用”。前者按切换规则进入新对话；当前对话不会在下载结束时被突然换版本。

## Preset 仓库标准

在现有声明格式上标准化，不另创一套平行的 Pi 包协议：

```text
package.json             # Pi 的 pi 资源声明；集合仓库可列出 wardrobe.presets
preset.json              # 单个 preset 的身份、兼容范围、依赖和资源选择
extensions/
skills/<name>/SKILL.md
prompts/
themes/
```

集合仓库使用 `presets/<slug>/preset.json` 和声明式索引；同仓库多个 preset 共享资源时仍使用明确的相对路径。现有 `presets/perfect-pi`、根目录单 preset 及已支持的仓库布局应有兼容导入路径。

仓库声明中不携带本机绝对路径、localhost 临时 Git 来源、token 或模型策略。导入支持粘贴标准 GitHub URL/简写及可选 ref；内部解析为确切提交或包版本后生成锁，不要求用户自己复制 SHA。稳定仓库身份、preset ID、安装版本、本地派生关系分开记录。非法路径、缺失资源和不兼容 schema 给出明确诊断。

## 启动路径与性能验收

启动仅读取当前选择及已准备好的资源描述；普通启动不做远端检查、不重装依赖、不启动额外 Pi 做探测、不重新完整散列所有旧版本。完整校验保留在安装/更新/显式诊断中；启动必须如实区分缓存校验结果与本次完整校验。

缓存按 preset 修订、Pi/Node 兼容信息、资源描述及本地资源变更失效，不能为提速继续加载已失效或丢失的资源。个人和项目技能变化应被发现，同名 skill 的优先级不能因取消探测而回退。发现变更后只重建受影响内容，不扫描所有保留版本。

已确认的验收：同机、同资源、相同网络及缓存条件下，至少三次预热后的启动中位数，相比原生 Pi 额外耗时不超过 500 ms；另报首次冷启动和完整 Perfect Pi 的实际耗时。不要用空 preset 结果代表完整 preset。保留旧修订从 1 个增加到 10 个，启动不应逐个完整校验。扩展自身不可避免的加载耗时与 Wardrobe 开销分开报告。

## 实施与迁移边界

此方向会替代 ADR-0003 中“用户在外部重新启动完整资源修订”的日常交互；保留其进程隔离和不可变修订的动机。ADR-0004 的历史会话绑定、更新追随与精确复现能力继续保留，但普通切换不改变启动默认。ADR-0001 的 manager 与参考 preset 分离、ADR-0002 的原生包生命周期继续保留。

现有 Perfect Pi 安装应通过导入已有计划和包树迁移，识别原始上游，移除对本地源码工作区和临时 localhost 服务的长期依赖。保留可恢复的旧安装；旧 `perfect-pi` 入口在迁移完成后提供兼容提示或转交，不在未验证时删除。

后续实现按依赖拆分：启动性能与当前版本读路径；原生扩展 bootstrap/首次归档；会话绑定与自动交接；composer 面板和默认值；标准仓库导入；整套/派生资源更新及 Pi 自更新集成；现有安装迁移与完整回归。每一阶段都需可运行的用户路径与真实 TUI 证据。
