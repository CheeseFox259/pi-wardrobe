# Pi Wardrobe 实机交接

2026 年 11 月 24 日 · macOS arm64 · Pi 1.6.0

## 当前功能与实机状态

- 日常入口是原生 `pi` 里的 `/wardrobe`。面板支持创建、导入、编辑、导出和切换预设，以及设置全局或项目启动默认。保存和安装产生独立修订，历史会话仍关联原版本。
- 实机将 Pi 从 1.3.0 升到 1.6.0。原日常预设先经 Update 安装兼容修订 1.0.4，再经 Maintain 安装页脚修订 1.0.5。1.0.5 已在该机器设为启动默认，原 Warp 中的旧 Pi 退出后重开并加载成功。上述预设版本号属于这台机器的本地修订。
- 页脚修订通过 `wardrobe:preset` 在现有 `@narumitw/pi-statusline` 中显示一次预设名。实机检查了直接启动、`/reload`、切换往返和 50 列窗口。深色主题、固定依赖和本地设备绑定经核对。页脚适配在日常预设的本地修订中，仓库提供通用的 presentation API。

## 更新与维护如何操作

1. 从检出的仓库根目录运行 `pi install "$PWD/packages/wardrobe"`。Pi 本体由 `pi update --self` 升级。
2. 在 Pi 中运行 `/wardrobe update <预设>`。审阅能力报告，确认要改什么、保留什么、怎样验收。批准会保存方案并结束报告回合，再次运行同一条命令开始实施。遇到明确需求时可用 `--request` 指定范围。
3. 只改一个功能时，用 `/wardrobe maintain <预设> --request "具体要求"`。例如让预设名移入现有增强页脚，并要求新会话、重载和切换均只显示一次。
4. 模型或操作员在候选里保存改动、决策和受影响的检查。用相应的 `update` 或 `maintain` 命令加 `--verify` 验收候选，达到 `READY_TO_INSTALL` 后加 `--apply` 并确认。可以先用 `/wardrobe use <修订>` 实机试用，最后用 `/wardrobe default <修订>` 设置日常启动版本。恢复时从版本列表选择旧修订，或通过 `/resume` 打开旧会话。

## Magpie 与 Pi 各自负责什么

Magpie 将模型目录同步到原生 Pi 的 `models.json`。Pi 用官方设置 `enabledModels` 决定默认模型列表和循环切换范围。实际配置使用下面的规则。

```json
{
  "enabledModels": ["magpie/**"]
}
```

Pi 在启动时计算这个范围。Magpie 同步增删后，新启动的 Pi 自动按当前目录纳入或移除模型。已打开的进程需要重启以刷新范围。实机的新进程显示 14 个 Magpie 模型，隔离的 Pi 终端测试也覆盖了新增与退役。日常启动仍使用 MiniMax M3.1 Flash / high。该规则属于本机 Pi 设置，模型、认证与设备绑定值由各自的原生存储管理。

## 验证到哪里

| 环节 | 结果 |
| --- | --- |
| 能力报告与人审 | 真实模型生成报告，人工在 Pi TUI 批准，状态跨进程保留。 |
| Update 实施 | 模型未及时保存成果。人工在同一个候选中完成最小兼容升级，再通过原生加载、技能契约与固定依赖检查。上游可选更新留待单独评审。 |
| Maintain 实施 | 模型把页脚需求理解为上一轮更新，未交付。人工在维护候选中完成适配。最终检查通过了原生加载、技能契约、TUI 身份和重载、扩展语法。 |
| 隔离检查 | 无凭据启动提示与实际扩展警告分开处理。页脚探针在隔离 Pi 中运行，设备绑定另外在正常启动时核对。 |
| 自动完成率 | 小型付费分段测试通过了报告与批准，未通过实施安装验收。实机交付用了人工接手。 |

发布前从暂存快照执行了 `npm ci`，两份工作流文件的 15 项测试全部通过。Pi 1.6.0 上的全量测试初跑为 341 项通过、6 项失败、1 项跳过。对齐人审流程与新版 Pi 输出后，三项相关断言在 Pi 1.6.0 上定向复验通过。其余三项是 Minimal Coding 和 Engineering 旧示例的启动测试，声明范围为 `>=1.1.0 <1.4.0`，在 Pi 1.3.0 上复验全部通过。全量套件没有在修改三处断言后重跑。

## 后续优先级

1. 报告以用户可见结果分组，写清变更、保留行为和验收。只在取舍会改变实施时加问题。
2. 在确认后直接提供「继续实施」，并给新回合明确的本轮任务、批准范围和第一个需保存的交付项。停滞时显示可继续的进度和具体操作。
3. 在使用、安装和默认设置的反馈里显示预设版本号。页脚继续只显示一次预设身份。
4. 下一次真实模型测试应覆盖批准后分回合实施、保存可独立验证的改动、安装和新会话启动，再判断人审是否缩短实施时间。
