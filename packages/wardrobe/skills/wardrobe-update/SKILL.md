# Update a preset

Call `wardrobe_workflow` with action `update`, `review: "human"`, and the chosen profile or local source. The result loads this method and the preset’s design policy. `NO_UPDATE` finishes the check.

When `planReview.phase` is `draft`, use the request and focused material in the handoff. Open the affected component contract or change evidence when it could change the recommendation.

Call `propose` in the user's language. For a single outcome, give one change row and one validation sentence. Each row names the `component`, user-visible `effect`, and `recommendation` (`adopt`, `adapt`, `defer`, or `preserve`). Include material preservation in that same row. Add `reason` when it explains a real trade-off or constraint. Use `summary` only to connect multiple outcomes. File edits and resource registration belong to their visible outcome. Describe what `validation` will show, and state compatibility as pending until checked. Add `question` only for an unresolved choice with a recommended option the user can approve or send back for revision.

Describe preservation at the level the user requested. For a resource addition, preserve the existing entries and behavior while Wardrobe updates the manifests to register the new resource. Validate retained values and loaded resources. Promise byte-for-byte preservation only for a file outside the planned edits and generated manifests.

Example row: `{"component":"状态栏","effect":"更换底部状态栏，保留原生文件写入。","recommendation":"adapt","reason":"旧扩展与当前 Pi 的写入机制冲突。"}`

The tool presents the report for confirmation. At `PLAN_APPROVED`, acknowledge approval in one sentence and end the report turn. Start implementation on the next user instruction with `resume` or another `/wardrobe update`. At `WAITING_INPUT`, tell the user the report is saved and stop. On a later user turn, `resume` shows the pending report again. Before implementation begins, `resume` with `revise: true` reopens the report using the user's feedback. If implementation reveals a material change to the approved scope, explain the finding and seek a decision before pursuing it.

For an approved scoped change, start with the affected candidate files and follow `nextCall`. To add a local skill, prompt, extension or theme, write its file and submit an `add` operation in `submission.resources` with `context.localPackageAlias`, its `kind` and relative `path`. Wardrobe updates the package and preset resource lists. Include a one-sentence `submission.summary` and one ready work item for a single requested outcome. Its checks start in the materialized package root. For a small text change, a Node assertion against the affected relative paths is enough to supplement Wardrobe's built-in loading check.

Use the complete item list to choose a dependency order. Call `focus` with an item ID to load its focused evidence; switching focus is allowed and does not gate saves for other items. The complete `changes` index retains every incoming change. For each required decision, record adoption, adaptation, or deferral with its concrete reason. Program checks establish basic loading compatibility; evaluate behavioral changes against the preset’s purpose.

For a compound request, use the component contracts to split the requested outcomes into bounded implementation items in `submission.work`. Do this in the same save as the relevant decisions. Each new item has `id`, `origins` (requirement/decision IDs from the returned items), `goal`, affected relative `paths`, exact `checks`, and optional `dependsOn` implementation IDs. An explicit Update request needs implementation coverage of `request`. Declare required local adaptations here instead of promising them only in a decision reason. Program-owned original/package adoption still occurs during verification. A single scoped change can use one item.

Focus an `implementation:<id>` to receive its goal, dependencies, paths and check plan. Implement the outcome, then save `{"work":[{"id":"<id>","ready":true}]}` inside `submission`. This records a claim for those exact candidate inputs; it does not prove verification. A changed affected path makes the claim stale. `check` runs the focused item's checks on the actual staged candidate before full coverage is complete. Fix a failing check, renew the claim and continue; final `verify` still runs all required gates. Independent paths can be worked on together, and cross-item saves remain available.

For skill files, `adopt` copies the upstream original during verification, `adapt` retains your candidate edits, and `defer` restores the local baseline. Use `adapt` when integrating upstream changes into local instructions or references. An adoption conflict names the edited file and decision ID; correct that decision to `adapt` and save before continuing.

For the chosen item, read its returned material and the applicable policy defaults, inspect affected implementation, then save the decision and check plan before investigating an independent item. Use `focus` to load that next item's evidence. Planned checks can run during `verify`. Expand investigation only to resolve a named missing fact, dependency, or failure that could change the decision. For an optional capability with ambiguous tradeoffs, preserve current behavior and record a reasoned deferral. If an explicit requirement depends on an unresolved choice, save a finite blocker and continue independent work.

Before widening an implementation investigation, update that work item's `missingFact` with `question`, `why` it can change the current decision, and a finite `nextStep`. Include this in an ordinary partial save; individual reads/edits need no administrative call. Retain already established facts and current candidate changes. Recovery names the unfinished outcome; resolve it, record its blocker, or continue an independent item. Rephrasing a summary or question does not renew the delivery allowance.

Make candidate changes and fill the returned `nextCall` save template: review fields belong inside `submission`, for example `{"action":"save","submission":{"decisions":[{"id":"<required decision ID>","action":"adapt","reason":"<concrete conclusion>"}],"checks":[]}}`. Resource `package` values are package aliases (for example `self` or `addon-7`), not npm/git sources; paths are safe relative resource paths. When removing a package declaration, include `retire` operations for its original catalog resources in the same save. Saving validates the merged resource draft and does not require completing another item or running verification. To pause one question, save an item-addressed blocker with a reason and finite next step, then focus independent work; resolve it with `submission.resolvedBlockers` before final verification. Saved decisions are merged by ID; a later decision replaces the earlier one. `details` recovers the item ledger and saved review.

Submit affected checks through `save`; `verify` runs them with a fresh `HOME` and Pi agent directory. For an earlier shell diagnostic, set both `HOME` and `PI_CODING_AGENT_DIR` to fresh disposable directories: candidate tests can invoke installers and write settings.

When required work is complete, call `verify`, optionally supplying further decisions and checks. It merges saved work, checks coverage, materializes actual dependencies, and tests the candidate. For verification failures, select one concrete failure or shared cause, inspect its named implementation and installed dependency, make the repair, and save the partial change before expanding to another failure. Save the repair decision describing the partial fix, then use `verify` to measure remaining failures; a failed verification reopens the repair item. A deferred optional capability preserves existing behavior; an unresolved required capability prevents installation.

At `READY_TO_INSTALL`, install with existing user authorization. `REVIEWED` means the review required no candidate change; `INSTALLED` confirms an installed revision, which remains inactive. Report the result and remaining questions. Pi owns its program upgrade, model selection, and authentication.
