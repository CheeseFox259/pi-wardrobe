# Component maintenance contracts

These are product choices for Perfect Pi. Explicit user requirements override defaults. New compatibility facts can require an adaptation or a finite blocker; they do not silently erase preservation requirements. Execution, investigation, partial saves, verification and installation belong to Wardrobe's shared method.

## Questions and interview UI

Default: adopt useful upstream interview methods and retain the local questionnaire interaction. Preserve recommended answers, amendment, prior answers, cancellation and non-interactive fallback. Explicit users can amend or reject the recommendation; cancellation grants no approval. A change may adapt the rendering or API but must preserve those outcomes.

Implementation: question/questionnaire extensions and the affected interviewing skill. Evidence: affected extension UI cases, including amendment, cancel and fallback. A successful extension load alone does not prove the interaction.

## Routing and workflow entries

Default: routing is advisory. Preserve prior answers and authorization through handoffs; use native Pi skill invocation. Preset update/maintain entries delegate execution to the shared Wardrobe methods and load this preset's policy. Historical workflow prose is reference material. Update reconciles supplied upstream changes; Maintain acts on the explicit request.

Explicit users may request execution or different scope. A route or new upstream method does not grant that authorization. Replace duplicate execution recipes with delegation while preserving useful companion references and local workflow purpose. Evidence: routing references, entry delegation, answer continuity, authorization and scope behavior in workflow-contract checks.

## Skills and local adaptations

Default: adopt compatible methodology; retain native Pi tools, local interaction choices and useful local-only skills. Upstream deletion or rename does not by itself authorize deleting local functionality. Optional capabilities with ambiguous value preserve current behavior through reasoned deferral.

Explicitly requested replacements can change behavior, with old resource retirement and surviving companions accounted for. Registry and lineage must describe the delivered content; model-owned implementation must not fabricate upstream ancestry. Evidence: affected skill behavior and references, skill audit, registry consistency and exported resource checks. Program-owned adoption of an original is distinct from a local adaptation.

## Native model selection and subagents

Default: a child inherits Pi's current model and thinking level. Role files and preset defaults do not pin a provider/model. Pi owns available models and credentials. Preserve explicit per-call or user-selected overrides and the existing consent boundary; resolve selected models through the native registry.

Replacing a legacy preset default includes removing its injection paths and migrating assertions that demanded that default. Preserve inheritance, explicit override precedence, rejected/cancelled selection and unavailable-model fallback. Implementation: subagent-policy, managed role files, research integration and their affected tests. A package version adoption does not alone discharge required local adaptations.

## Compaction and reducer selection

Default: normal compaction uses Pi's native selection. Preserve deliberate user overrides, consent/cancellation and safe fallback through the native registry. A background reducer may retain its explicit bounded consent/budget mechanism; it must not reintroduce preset provider defaults.

Implementation: compaction-model/settings, SoL-Pi reducer adapter and managed config. Evidence: native inheritance, explicit override, cancellation, missing registry entry/fallback and phase/consent behavior. Replace old provider-default assertions with these outcomes, while retaining independent product acceptance.

## SoL-Pi runtime and upstream capabilities

Default: runtime remains the CheeseFox259/SoL-Pi fork at its own reviewed pin. NVlabs/SoL-Pi supplies upstream capability changes for the local adapter. Their commits belong to separate repository lineages. Adapting an NVlabs capability does not change the fork pin.

Preserve bounded then_run validation, native guarded tool execution, exact observation recall, structured nested-tool results and consent/budget ownership. Optional capabilities that cannot be safely adapted can be deferred with a concrete limitation. Explicit runtime replacement requires a compatible replacement decision and preserved behavior; it is not implicit in an upstream update. Evidence: actual checkout/loading and affected fusion, recall, nested calls, phase and consent checks. Loading proves compatibility only within its scope.

## Statusline, theme and rendering

Default: use @narumitw/pi-statusline and Pi's built-in dark theme; retire archived ccstyle package/resources and its write takeover. Pi retains native tool execution and write ownership. Wardrobe's identity widget remains above the composer by default.

An explicit identity-placement request can move it into the statusline. Consume the public wardrobe:preset event before session_start, clear the default wardrobe widget, render one native status entry and unsubscribe on shutdown. Preserve a single correct identity across startup, reload and switches; switches use a new runtime. Implementation uses public Wardrobe presentation and Pi APIs. Evidence: selected resources, native startup/reload, identity uniqueness and switch behavior. The later placement request is not part of an earlier footer-package replacement unless explicitly requested there.

## Managed MCP and personal configuration

Default: adopt compatible integration fixes while preserving explicit allowlists, user-added entries, disabled state and managed ownership. Optional broad discovery or automatic adoption is deferred. Authentication and device-local values remain outside portable preset content.

Explicit user changes can alter the requested server selection without erasing unrelated personal entries. Evidence: managed-MCP configuration cases and affected startup/selection behavior. Legacy installer tests are relevant only when changing that installer; checks run in disposable HOME/Pi directories supplied by the shared workflow.
